Создан 16 июня 2026, обновлён 17 июня 2026. Документ для согласования с

## Baseline (снят 17.06, окно 08–16.06, честным методом)

Одна команда: `python scripts/weekly_kpi.py` → сохраняет JSON для сравнения
неделя-к-неделе. Метод строгий (URL + бренд+заголовок ≥85, как воронка).

| Метрика | Baseline | Примечание |
|---|---|---|
| **Покрытие** (собрали из опубликованного) | **13%** (7/53) | day-aligned: только за дни, когда прогон РАБОТАЛ; **не 83%** |
| **Uptime прогона** | **3 из 9 дней** | новая метрика — простой искажал покрытие |
| **Precision показа** (редактор оставил) | **58%** (41/71), окно 08–16.06 | по комментариям редактора — главная цифра «правильности» |
| Правильность разделов | 73% (11/15) | мала И смещена — см. §2 |
| Правильность отклонения (прокси) | 99% (535/540) | прокси, завышено |
| ~~Найдено-подтверждено~~ (наше→архив) | 8% (15/177) | НИЖНЯЯ оценка, ДРУГАЯ метрика, НЕ главная — см. §2 |

⚠️ **Главный честный вывод недели:** покрытие за эту неделю почти НЕ измеримо.
За окно редактор опубликовал ~303 новости; day-aligned исключает 250 в дни
без прогона → знаменатель покрытия 53. Из 3 дней, когда прогон работал
(9, 13, 16.06), публикации редактора в окне пришлись только на 9 июня — отсюда
7/53. То есть низкая цифра — это в основном **простой + рассинхрон
расписания**, а не качество поиска. Чтобы покрытие стало чистой цифрой, нужны
ежедневные прогоны. От этой базы и считаем рост.

(Воронка промахов в §0 считает по своему 8-дневному окну = 263 публикации —
другое окно, поэтому знаменатель там иной.)

## 0. Главное, что нужно сказать сразу

**Цифра «83% покрытия» — завышена и вводит в заблуждение.** Она считается
старым «нестрогим» методом (совпадение по бренду/модели «где-то в тексте»),
который сам проект уже признал ошибочным ещё в мае. Честное покрытие, строгим
методом — **~13% (7/53, day-aligned)**, а не 83%. (Не путать с архивным матчем
8% — это другая метрика, см. §2.) Это не обман: команда сама задокументировала
проблему, но старый KPI остался. Любое согласование цели должно стартовать с
правильной цифры.

**Где главная дыра — теперь известно.** Воронка промахов (после фикса, см. §1)
раскладывает ВСЕ 263 публикации окна по стадии:

| Стадия | Доля | Что значит |
|---|---|---|
| **S2** | **81%** (213) | источник У НАС В СПИСКЕ, но статью не собрали (краулинг) |
| S1 | 10.6% (28) | источника нет в списке |
| S3+S4 | 1.5% (4) | классификатор отсёк (эвристика / ИИ) |
| S0/S5 | 6.8% (18) | собрали и показали — это НЕ промах |

Промах по сбору (S1+S2) = **91.6%**, по классификатору (S3+S4) = 1.5%.

Проверка достоверности: у **95% непойманных лучший кандидат у нас набирает
<70** (нет близкого совпадения) — это реальные дыры. У ~12 публикаций есть
near-miss (70–84), где S2 мог быть слегка завышен сопоставлением.

⚠️ Оговорки воронки (честно): S1 — **верхняя оценка** (считается по выбранному
редактором Outer Link; первоисточник типа moex/tass мы часто берём через
агрегатор, так что реальный source-gap меньше). Проверка «95% без кандидата»
сама ограничена кросс-языковым сопоставлением заголовков. Но даже с этими
оговорками вывод устойчив: **главный рычаг — краулинг по источникам, которые
УЖЕ есть** (нет RSS / JS-рендер / пейволл / пагинация), а НЕ добавление новых
источников и НЕ классификатор.

**Цель «95% правильно за 1–2 месяца» — нереалистична** (см. §4). Реалистичная
согласуемая цель — другая (§3, §4).

## 1. Что уже сделано (проверено)

Костяк рабочий: сбор (~360 записей-источников в листе ≈ 290 уникальных доменов
после нормализации; воронка S1/S2 считает по 290 доменам), 3×/день по
расписанию → классификация (Haiku) → кластеризация (ИИ-редактор) → пуш в лист
редактора. Шаги 4–5 (кластеры + пуш) пока запускаются вручную.

За последние сессии **реально включено в прод**: версионирование кэша
классификатора, фикс покрытия (молча пропускавшиеся источники),
heuristic-section, устойчивость прогона (3 падения → починены),
детерминированный дедуп против архива редактора (в прогоне видна строка вида
«N source URLs + M recent titles loaded»).

**Новое за 16–17.06 (инструменты честного отслеживания):**
- **Покрытие стало day-aligned** — считается только за дни, когда прогон
  работал; простой выведен в отдельную метрику uptime (не штрафует покрытие).
- **Precision = по комментариям редактора** (общий код с `scorecard.py`,
  расходиться не могут); архивный матч понижен до нижней оценки.
- **Лист «Непокрытые (анализ)»** — `miss_funnel.py --to-sheet --ai` пишет в
  таблицу все непокрытые публикации со стадией (S1–S4, с цветом), причиной,
  доменом и **ИИ-рекомендацией по источнику** (гипотезы помечены, не-авто
  источники типа moex/cbr помечены «убрать»).

⚠️ **Честно про процесс — два скрытых бага, найдены и исправлены:**
1. (ранее) Увод подозрительных строк в лист проверки ронял весь пуш
   runtime-ошибкой; поймал независимый аудит, исправлено.
2. (17.06) Воронка промахов **молча возвращала 0 публикаций** — её парсер
   дат понимал только ISO, а архив сейчас в формате Excel-serial. Ключевой
   диагностический инструмент был сломан, и этого никто не видел. Исправлено:
   один общий парсер дат (`core/sheet_dates.py`) для обоих скриптов. Урок:
   «зелёный запуск» ≠ «правильный результат».

Эти случаи прямо мотивируют гейты §3: линтер (pyflakes), 661 тест, и проверку
результата (а не только «запустилось») перед словом «готово».

## 2. Метрики (одно честное определение на каждую)

Словом «recall/покрытие» в проекте называли ТРИ разные вещи с разными числами
(86% / 82% / ~13%). Фиксируем по одному определению:

| Метрика | Что значит | Текущее (честно) | Как мерить |
|---|---|---|---|
| **Покрытие** | из опубликованного — сколько собрали (за рабочие дни) | **~13%** (day-aligned) | `weekly_kpi.py` / `miss_funnel.py`, строгий матч |
| **Uptime** | в скольких днях прогон реально отработал | **3/9** | `weekly_kpi.py` |
| **Precision показа** | из показанного — сколько редактор оставил | **~58%** (окно 08–16.06) | `weekly_kpi.py` / `scorecard.py` по комментариям |
| **Точность раздела** | из показанного — верный ли раздел | **~73%** (n=15, мала+смещена) | weekly_kpi; нужно расширить выборку |
| **Жалоб на прогон** | сколько строк редактор пометил «не так» | мерить с прогона | лист редактора, колонка комментариев |

**Важно про «правильно найдено».** Раньше как «правильность» иногда читали
архивный матч (**8%**, 15/177). Это ВВОДИТ В ЗАБЛУЖДЕНИЕ: он требует, чтобы
редактор опубликовал ровно ту же статью и она совпала по заголовку — его
занижают дыры прогонов и кросс-язык. **Честная «правильность показанного» =
precision по комментариям ≈ 58%**, а не 8%. Архивный матч (8%) оставлен только
как строгая нижняя оценка с пометкой; 13% — это ПОКРЫТИЕ, другая метрика, его
сюда подмешивать нельзя.

⚠️ Оговорки к precision 58%:
- **scope.** 58% (41/71) посчитан за окно 08–16.06. Если в окне нет свежего
  фидбэка, скрипт молча берёт all-time — здесь scope=window, цифра недельная.
- **смещение.** 71 прокомментированная строка — НЕ случайная выборка
  показанного (редактор комментирует выборочно, чистое часто пропускает
  молча). Поэтому 58% — ни чистый «пол», ни проектируемое на прод число.
  Несмещённый precision требует репрезентативной выборки (см. ниже).
- **раздел 73% (11/15)** считается ТОЛЬКО на 15 строках, совпавших с архивом
  (подмножество found_right) — не на всех показанных; выборка мала И смещена.

**Что нужно для метрик, которым можно верить:**
1. Заморожены определения (сделано: один recall = строгий, один precision =
   комментарии).
2. Репрезентативная выборка для precision (сейчас фидбэк смещён к проблемным).
3. Расширить разметку разделов (n≈15 — мало).

## 3. Процесс (недельный цикл + гейты)

**Еженедельно (follow-up с руководителем):**
- `weekly_kpi.py` — покрытие (day-aligned) + uptime + precision ВМЕСТЕ;
- `miss_funnel.py --to-sheet --ai` — лист «Непокрытые (анализ)»: куда уходят
  промахи и что чинить по каждому источнику;
- 1 число «жалоб на прогон» от редактора.

**Гейты на каждое изменение (чтобы не было багов как выше):**
- `pyflakes scripts/ src/` — ловит ошибки имён;
- `pytest` (661 тест);
- `eval_diff.py` — прогон до/после на замороженном сете (анти-маятник);
- проверка РЕЗУЛЬТАТА, а не только «запустилось» (баг с воронкой проскочил
  именно потому, что «запускалось» без ошибки).

**Поток данных для обучения:** редактор размечает ~50 отклонённых/нед в листе
«Разметка отклонённого (ИИ)» → негативы копятся → retrieval растёт.

## 4. Цель на 1–2 месяца (достижимая, измеримая)

**Почему НЕ 95%:** два главных рычага ВНЕ модели — (1) покрытие (91.6%
промахов — это сбор, не классификатор); (2) дубли — вторая по величине жалоба
(7 из ~32), но единственная без дешёвого софт-решения (нужен живой портал по
API). Топ-жалоба — «не нужно» (16 из ~32), её растим разметкой. Плюс «вкус»
редактора субъективен (потолок согласия ~80–85% даже у человека).

(Про тренд precision честно: сравнивать пока НЕ с чем — единый замер заведён
только этой сессией; прошлые цифры (42% / 57.6% / 58%) мерились разными
методами и несравнимы. Аргумент «95% нереалистично» опирается на структурные
рычаги выше, а не на «precision не растёт».)

**Предлагаемая согласуемая цель (1–2 мес), всё измеримо:**

1. **Uptime: 3/9 → ежедневно (≥6/7 дней).** Самый дешёвый и быстрый рычаг и
   ЕДИНСТВЕННОЕ твёрдое обязательство на неделю 1 — без регулярных прогонов
   покрытие просто не существует как цифра. Меряется `weekly_kpi.py`.
2. **Покрытие — целевой % зафиксируем ПОСЛЕ 1–2 чистых недель** (сейчас 13%
   стоит на 3/9 днях — это ещё не настоящая база, ставить цифру-обязательство
   рано). Рычаг известен: **S2** (источники у нас ЕСТЬ, но не собираем) —
   чинить RSS / JS-рендер / пейволл / пагинацию по топ-доменам из листа
   «Непокрытые (анализ)» (измеренный топ S2: tass.ru=13; полный список — в
   листе за чистую неделю). Меряется `miss_funnel.py` до/после.
3. **Precision показа: 58% → ~65%** по комментариям редактора. Основной
   рычаг — **чистка вредных правил блэклиста по разметке**. (retrieval-
   классификатор в прошлой сессии дал +3.8пп на ТОНКОЙ базе 88 негативов на
   замороженном eval-сете (57.6→61.4, ДРУГОЙ метрикой), но в одиночку РОНЯЕТ
   разделы (60→43%), это НЕ drop-in и в проде НЕ подтверждён — гипотеза,
   требующая негативов в масштабе; с 58% арифметически НЕ складывается.)
4. **Дубли: цель −30–50% видимых (ориентировочно)** — достижимая доля зависит
   от того, что даст портал. Единственное измерение дешёвого снапшот-подхода —
   26% catch / 20% ложных — недостаточно; нужен **доступ к порталу по API**.
5. **Жалоб на прогон: видеть тренд** (завести метрику, цель < 15).

**Что нужно от руководителя для цели:** (а) согласие на правильную базовую
цифру (не 83%); (б) **доступ к порталу/выгрузке опубликованного по API** —
без него дубли не закрыть в принципе; (в) по возможности — чтобы редактор
зафиксировал спорные правила (что «не нужно»), иначе субъективный потолок
~80–85%.

**Честный итог:** «95% правильно» как одно число недостижимо за 1–2 месяца и
плохо определено. Достижимо: **наладить ежедневный прогон (uptime — твёрдая
цель недели 1), поднять покрытие через починку краулинга существующих
источников, растить precision по разметке — и видеть прогресс по 5 осям каждую
неделю, а не через жалобы.** Это и есть то, что просит руководитель («метрики,
процесс, цель»), просто с реальными числами.
